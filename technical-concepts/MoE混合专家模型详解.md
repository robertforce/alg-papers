# MoE：混合专家模型的概念、原理与计算过程

## 1. MoE 是什么？

MoE（**Mixture of Experts，混合专家模型**）将一个变换拆成多个专家网络，再由路由器根据输入决定如何组合专家输出。

> 在 Transformer 的稀疏 MoE 中，每个 token 通常只运行少量专家，从而用较小的激活计算量，访问一个总参数量更大的模型。

本文主要讨论 **token 级稀疏 FFN-MoE**：专家是替代普通 FFN 的前馈网络，路由单位是 token。MoE 是更一般的思想，也可以出现在其他模型结构中。

需要区分：

- **稠密 MoE：**运行所有专家，再加权汇总；
- **稀疏 MoE：**仅运行被选中的少量专家。

只有后一种才带来典型的条件计算优势。

## 2. MoE 在 Transformer 中的位置

普通块：

```text
输入 → Attention → 残差 → 普通 FFN → 残差 → 输出
```

MoE 块：

```text
输入 → Attention → 残差 → Router + 多个专家 → 残差 → 输出
```

通常是 FFN 子层被替换，而不是每个专家都是一整套 Transformer。

专家可以使用 [SwiGLU 门控前馈网络](./SwiGLU门控前馈网络详解.md)：

$$
E_i(x)=\left[\operatorname{SiLU}(xW_{g,i})\odot(xW_{u,i})\right]W_{d,i}
$$

不同专家具有独立参数。它们不必提前被标成“语言专家”“商品专家”等人工类别，分工通常在训练中形成；是否形成清晰语义专长需要额外分析，不能从名字推断。

## 3. 基本公式：评分、选专家、加权汇总

假设有 $E$ 个路由专家，每个 token 选 $k$ 个。

### 3.1 Router 生成分数

对 token 表示 $x\in\mathbb R^D$：

$$
a=xW_r+b_r,\qquad W_r\in\mathbb R^{D\times E}
$$

得到 $E$ 个路由 logit。

一种常见做法是：

$$
s_i=\operatorname{softmax}(a)_i
$$

也有架构使用独立 sigmoid：

$$
s_i=\sigma(a_i)
$$

**softmax 路由不是 MoE 的唯一形式。**后续公式使用一般分数 $s_i$。

### 3.2 选择 top-k 专家

$$
\mathcal I(x)=\operatorname{TopKIndices}(s,k)
$$

例如 8 个专家中，当前 token 只运行专家 2 和 6。

Top-k 通常表示硬选择，不是从分布随机抽样；有些训练方案会引入噪声，但属于额外设计。

### 3.3 确定组合权重

一种常见实现是将选中分数重新归一化：

$$
\alpha_i=\frac{s_i}{\sum_{j\in\mathcal I(x)}s_j},\qquad i\in\mathcal I(x)
$$

然后：

$$
y=\sum_{i\in\mathcal I(x)}\alpha_iE_i(x)
$$

不同 MoE 架构也可能保留原始概率、添加缩放系数或采用其他门权重，不能将上述归一化视为所有 MoE 的固定规则。

## 4. 完整张量计算过程

以下为说明性配置：

```text
batch B = 2
序列长度 L = 100
token 数 T = B × L = 200
模型维度 D = 512
路由专家数 E = 8
每个 token 选择 k = 2 个专家
每个专家的 SwiGLU 中间维度 F = 256
```

### 第一步：展平 token

```text
输入 X：[2, 100, 512]
展平后：[200, 512]
```

标准 token 级路由对每个位置独立做决定，不是一个 batch 共用同一组专家。

### 第二步：计算路由分数

$$
A=XW_r
$$

```text
Wr：[512, 8]
A：[200, 8]
```

经 softmax 或 sigmoid 后，每行表示一个 token 对 8 个专家的分数。

### 第三步：选 top-2

```text
expert_indices：[200, 2]
expert_weights：[200, 2]
```

因此共有：

$$
T\times k=200\times2=400
$$

个 token—expert 分配关系。

这不是运行 400 个不同专家，而是把 200 个 token 各送入两个专家。8 个专家接收的 token 数量可以不同。

### 第四步：按专家分桶与分发

例如：

```text
专家 0：接收 token [0, 4, 9, ...]
专家 1：接收 token [2, 7, 9, ...]
...
专家 7：接收 token [1, 5, 8, ...]
```

同一 token 可以出现在两个桶里，每个桶中的 token 使用该专家的独立参数。

若 token 平衡分布，每个专家平均处理：

$$
\frac{Tk}{E}=\frac{400}{8}=50
$$

个 token。真实数量由路由结果决定。

### 第五步：运行专家

专家 $i$ 收到 $T_i$ 个 token：

$$
X_i\in\mathbb R^{T_i\times512}
$$

其 SwiGLU 计算：

```text
输入：[Ti, 512]
gate/up：[Ti, 256]
逐元素相乘：[Ti, 256]
输出：[Ti, 512]
```

一个专家桶内可批量计算。普通专家 FFN 不在这些 token 之间做 Attention；分桶是计算调度，不是新增跨 token 信息交互。

### 第六步：收回结果并加权合并

对每个 token，收回它所选的两个专家输出：

$$
y_t=\alpha_{t,i}E_i(x_t)+\alpha_{t,j}E_j(x_t)
$$

得到：

```text
合并后：[200, 512]
恢复形状：[2, 100, 512]
```

最后与残差流相加。概念伪代码：

```python
scores = router(x)  # [T, E]
indices, weights = select_and_weight(scores, k=2)

buckets = dispatch_by_expert(x, indices)
expert_outputs = run_experts(buckets)
y = gather_and_weighted_sum(expert_outputs, indices, weights)
```

## 5. 一个数值例子

假设有 4 个专家，选择 top-2。某个 token 的路由分数为：

$$
s=[0.1,0.5,0.3,0.1]
$$

选中专家 1 和专家 2。若对选中分数重新归一化：

$$
\alpha_1=\frac{0.5}{0.8}=0.625,\qquad
\alpha_2=\frac{0.3}{0.8}=0.375
$$

假设：

$$
E_1(x)=[2,0],\qquad E_2(x)=[0,4]
$$

则：

$$
y=0.625[2,0]+0.375[0,4]=[1.25,1.5]
$$

专家 0 和专家 3 没有执行，所以没有它们的专家计算成本。不过 Router 仍需要给所有候选专家评分。

## 6. Shared Expert：为什么有的专家始终运行？

一些架构将专家分成：

1. **共享专家：**每个 token 都运行；
2. **路由专家：**每个 token 只选择少量运行。

一种形式是：

$$
y=E_s(x)+\gamma\sum_{i\in\mathcal I(x)}\alpha_iE_i(x)
$$

其中 $E_s$ 是共享专家，$\gamma$ 是路由分支缩放系数。

设计动机是让共享专家承载较通用的变换，路由专家补充输入相关能力。但这是一种架构意图，不保证学习后一定形成可解释的通用/专属分工。

共享专家的参数和计算必须计入激活预算。若有多个共享专家，则将其输出相加或按架构规定组合。

## 7. 总参数量、激活参数量和 FLOPs 的区别

假设每个专家参数量约为 $P_e$，路由专家数为 $E$，每个 token 选 $k$ 个，无共享专家。

### 7.1 总专家参数量

$$
P_{\text{total,experts}}=EP_e
$$

### 7.2 每个 token 激活的专家参数量

$$
P_{\text{active,experts}}=kP_e
$$

若 $E=64,k=2$，总专家容量是 64 个专家，但每个 token 只执行其中 2 个。

这两个口径只计算专家部分；整个模型还要加上 Attention、Router、Embedding 等组件。

另外，“每 token 激活参数量”不等于整个 batch 只访问这些参数。不同 token 可能覆盖全部专家。

### 7.3 SwiGLU 专家的例子

忽略偏置，每个专家参数量为：

$$
P_e=3DF
$$

单 token 的专家矩阵乘成本约为：

$$
\operatorname{FLOPs}_{\text{experts}}\approx6kDF
$$

总专家参数为：

$$
3EDF
$$

所以在固定 $k,D,F$ 时，增加 $E$ 可以增加专家总容量，而不按比例增加每个 token 的专家计算。不过 Router 的评分成本随 $E$ 增长，通信和系统开销也可能变化。

**MoE 并不自动比任意稠密 FFN 计算更便宜。**比较时需要同时说明稠密 FFN 宽度、单专家宽度、选中专家数、共享专家预算等条件。

## 8. 为什么 MoE 不一定让训练或推理更快？

稀疏激活减少了需要执行的专家网络数量，但还引入了调度成本。

### 8.1 Dispatch 和 Combine

需要根据路由结果重排 token，运行不同专家，再恢复原位置。

### 8.2 跨设备通信

若专家分布在不同 GPU，token 需要被发送到目标专家所在设备，再把输出送回。专家并行常涉及 all-to-all 通信，但具体通信形式取决于部署方式。

### 8.3 负载不均衡

如果大部分 token 都选择少数专家，这些专家成为瓶颈，其他专家闲置。

### 8.4 小矩阵效率

专家很多、每个桶 token 很少时，矩阵乘可能过小，GPU 利用率不足。

因此：

> 更低的理论激活 FLOPs，不保证更低的端到端延迟。MoE 的收益取决于专家批量、负载均衡、并行布局和通信效率。

即使只激活少量专家，也仍需要存储整个模型的专家权重，或通过分片/卸载管理它们；显存不会自动缩到激活参数量。

## 9. 专家负载均衡与容量限制

### 9.1 为什么会路由塌缩？

训练早期某些专家略占优势，Router 可能不断把更多 token 分给它们；它们获得更多训练机会，又进一步占优，形成正反馈。

### 9.2 常见均衡方法

- 在任务损失外添加负载均衡辅助损失；
- 给路由评分或选择引入噪声；
- 调整路由偏置或采用其他均衡调度；
- 使用更适合目标硬件和 batch 分布的路由策略。

不同架构不一定同时使用这些方法。

一种常见辅助项形式为：

$$
\mathcal L_{bal}=E\sum_{i=1}^{E}f_i p_i
$$

其中 $f_i$ 表示专家实际接收 token 的比例，$p_i$ 表示对应的平均路由概率。具体归一化和 top-k 扩展方式因实现而异。这是一个代表性例子，不是所有 MoE 或 OneTrans-V2 的固定损失。

### 9.3 专家容量

有些实现给每个专家设置容量，概念上可写为：

$$
C\approx\left\lceil c\frac{Tk}{E}\right\rceil
$$

其中 $c$ 为 capacity factor。

超过容量的 token—expert 分配可能被丢弃、改派或通过其他机制处理。也有 dropless 实现不丢 token，通过动态形状和调度承接全部分配。

**token 丢弃不是 MoE 的必然属性。**

## 10. Router 是怎么训练的？top-k 能反向传播吗？

### 10.1 专家参数的梯度

一个 token 的任务损失会更新被它选中、且贡献输出的专家。未被该 token 使用的专家，不从该 token 的专家输出路径获得梯度；但可能被其他 token 更新。

### 10.2 路由权重的梯度

若组合权重依赖 Router 分数，损失可以沿“加权汇总 → 路由权重 → Router”路径传播。

### 10.3 离散选择本身不可普通微分

“哪个专家进入 top-k”的索引切换是离散操作。常规实现并不是对索引求连续导数，而是在当前选择下对可微的分数/权重路径反传，再结合均衡机制等训练 Router。

一个容易忽略的特殊情况：若 top-1 后又严格将唯一选中权重归一化成 1，那么该组合系数本身不再提供随分数变化的任务梯度。实际架构可能保留原始门概率，或者采用额外损失及其他梯度机制。因此不能笼统说“任意 top-k 实现都能靠相同路径学好 Router”。

## 11. Softmax Router 与 Sigmoid Router

### Softmax

$$
s_i=\frac{e^{a_i}}{\sum_j e^{a_j}}
$$

- 所有分数之和为 1；
- 专家之间存在归一化竞争；
- 改变一个 logit，会影响其他专家的概率。

### Sigmoid

$$
s_i=\frac1{1+e^{-a_i}}
$$

- 每个专家独立获得一个 $(0,1)$ 分数；
- 多个专家可以同时获得高分；
- 评分本身不要求在所有专家间总和为 1。

但如果选中专家后重新归一化，最终组合权重仍在选中集合内耦合。Sigmoid 并不意味着整个路由过程完全独立，也不意味着自动获得负载均衡。

## 12. OneTrans-V2 中的对应设计

根据 [OneTrans-V2 原文](../../OneTransV2.2609.28589v1.pdf) §4.3：

- FFN 子层使用稀疏 MoE；
- 专家是中间层较窄的 SwiGLU 网络；
- 一个共享专家始终激活；
- Router 使用 sigmoid 评分并选择固定数量的最高分路由专家；
- 对选中分数重新归一化，再乘固定缩放系数；
- 输出为共享专家输出，加上选中路由专家输出的加权和。

对应概念公式：

$$
y=E_s(x)+\gamma\sum_{i\in\mathcal I(x)}
\frac{\sigma(a_i)}{\sum_{j\in\mathcal I(x)}\sigma(a_j)}E_i(x)
$$

本文中的 8 专家、top-2、具体宽度、均衡损失与容量公式是通用说明，**不是论文公开的生产配置或训练细节**。论文没有完整披露专家总数、激活数等参数，也不能据通用 MoE 实践补全其实现。

## 13. 与其他技术的边界

| 技术 | 主要解决什么 | 与 MoE 的关系 |
|---|---|---|
| SwiGLU | 一个 FFN 内部的非线性和门控 | 可以作为专家内部结构 |
| GQA | 减少 Attention 的 K/V 头与缓存 | 可以与 MoE 同时使用 |
| SNT | 多个曝光共享历史序列计算 | 与专家路由属于不同层面的复用 |
| 稀疏 Attention | 减少 Query 读取的 token 范围 | 与选择 FFN 专家不是一回事 |
| 多任务输出头 | 对同一表示预测多个目标 | 不等于 MoE 专家路由 |

尤其注意：召回、粗排、精排是业务阶段，并不天然等于三个 MoE 专家；是否让不同阶段偏向不同专家，是另一个需要实证分析的问题。

## 总结

**稀疏 MoE 为每个 token 选择少量专家执行，用条件计算扩展模型总容量。理解它要同时看总参数、每 token 激活预算、路由训练和系统通信；SwiGLU 决定专家内部怎么算，Router 决定当前 token 找哪些专家。**
